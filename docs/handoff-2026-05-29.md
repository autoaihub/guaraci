## Tarefa 1 — Fonte NASA POWER (`nasa_power`)  ✅ implementada, testada, commitada

**O que fiz e por quê.** Integrei a NASA POWER API (Prediction Of Worldwide Energy
Resources) como nova fonte primária de séries climáticas/meteorológicas. É a fonte
oficial direta (NASA serve os dados; sem intermediário curador), aderente ao
Princípio 20 do vogel-stack. Cobre o Brasil inteiro (grade global ~0.5°×0.625°),
não exige autenticação e responde JSON — encaixe natural no padrão das fontes de API
do Guaraci.

**Arquitetura (espelha `guaraci/opendatasus/`):**
- `guaraci/nasa/__init__.py` — exporta `NasaPowerClient`, `NasaPowerClientError`,
  `NasaPowerDataSource`.
- `guaraci/nasa/client.py` — `NasaPowerClient` sobre `urllib` (stdlib, sem dep nova),
  com a mesma taxonomia de erro do OpenDataSUS (`category`/`retryable`/`hint`,
  `with_context`). Método `temporal_point(temporal, parameters, lat, lon, start, end,
  community)`.
- `guaraci/nasa/power.py` — `NasaPowerDataSource(DataSource)`: valida entradas, chama
  o client, parseia `properties.parameter.<VAR>.<período>` numa tabela larga (1 linha
  por período, 1 coluna por variável) + colunas derivadas `period/date/year/month/day`
  e `latitude/longitude/elevation`. Exporta csv/parquet/sqlite, escreve `manifest.json`
  (`DownloadManifest`) e emite eventos de progresso compatíveis com `jobs.py`.
- `guaraci/services/downloads.py` — adapter fino `NasaDownloadSource` + registro da
  fonte `nasa_power` (mode `"nasa power api"`) + `_normalize_nasa_power_params`.

**Decisões tomadas + justificativa:**
1. **Pacote próprio `guaraci/nasa/`** em vez de reusar OpenDataSUS: a NASA é outro
   publisher, com produtos heterogêneos (POWER/FIRMS/GPM). Mantém coesão e isola risco.
2. **Client stdlib, duplicando um pouco da plumbing HTTP do OpenDataSUS** em vez de
   extrair uma base compartilhada: extrair base mexeria em `opendatasus/client.py`
   (fonte que já funciona) → risco. A duplicação é isolada e reversível. *Futuro:*
   extrair `BaseHttpJsonClient` quando houver 3+ clients.
3. **`latitude`/`longitude` como entrada nativa** (tipo `string`, parse→float no
   datasource, pois o sistema de tipos do schema não tem float). Mapear município→
   centroide ficou como trabalho futuro (exige dataset de coordenadas do IBGE, que é
   outra integração de fonte primária). Escolha conservadora = expor o contrato nativo
   da API agora, conveniência depois.
4. **Lista curada de `parameters`** (14 variáveis) como `allowed_values`, em vez de
   aceitar o catálogo POWER inteiro (centenas). Dá dropdown discoverable na UI
   schema-driven e evita erros. **Validei as 14 ao vivo** contra o endpoint daily/AG
   (todas retornaram). Power users que precisem de variáveis exóticas: trabalho futuro
   (ex.: parâmetro livre + validação contra catálogo POWER).
5. **`temporal` daily + monthly.** O agregado anual mensal do POWER (`YYYY13`) é
   preservado sem perda como `month=13` (sem `date`) — filtrar `month <= 12` isola os
   meses verdadeiros. Documentado.
6. **`fill_value` lido de `header.fill_value`** (não hardcode -999) e convertido para
   null. Confirmei via probe ao vivo que o sentinela vive nesse campo.
7. **`output_format` default `None`** + warning quando não há artefato (igual
   OpenDataSUS/PySUS), por consistência de contrato, mesmo que um run default não gere
   arquivo. `keep_raw` salva o JSON bruto.
8. **Branch dedicada** (ver alerta acima).

**Como verifiquei (gates):**

## Tarefa 2 — Fonte NASA FIRMS (`nasa_firms`)  ✅ implementada, testada, commitada, pushada

**O que fiz e por quê.** Integrei a NASA FIRMS (Fire Information for Resource Management
System) — detecções de foco de calor/incêndio ativo (MODIS/VIIRS), near-real-time e
standard-processing. Fonte primária direta (`firms.modaps.eosdis.nasa.gov`). Relevante
para saúde respiratória (fumaça/queimadas × internações por doença respiratória).

**Arquitetura.** `NasaFirmsClient` (em `guaraci/nasa/client.py`, CSV via `urllib`) +
`NasaFirmsDataSource` (`guaraci/nasa/firms.py`). Registrado como `nasa_firms`
(mode `"nasa firms api"`) reusando o adapter `NasaDownloadSource` +
`_normalize_nasa_firms_params`.

**Decisões + justificativa:**
1. **MAP_KEY só por env `GUARACI_FIRMS_MAP_KEY`** (ou injeção em teste), **nunca** como
   parâmetro de job. Motivo de segurança: jobs são persistidos em disco
   (`data/jobs/download_jobs.json`) com seus params; um segredo ali vazaria. O MAP_KEY
   também é redigido das mensagens de erro do client e **não** entra no manifest.
2. **Parâmetro `product` em vez de `source`.** A API FIRMS chama isso de "source", mas
   `DownloadService.run(source, **params)` reserva o argumento `source` → colisão real
   (`got multiple values for 'source'`). Renomeei para `product` no schema/datasource;
   o client mantém o nome nativo `source` internamente. (Bug pego por teste antes do
   commit.)
3. **Janela fatiada em blocos de ≤10 dias** (limite `day_range` do FIRMS) e CSVs
   concatenados. Parsing **genérico** (sem colunas hardcoded) → robusto às diferenças
   MODIS vs VIIRS. Coluna `firms_product` adicionada para procedência.
4. **Brasil por padrão** via `country=BRA`; `area` (bbox `oeste,sul,leste,norte` ou
   `world`) opcional e tem precedência.
5. **Client FIRMS auto-contido** (2º client NASA). Mantive minha regra documentada:
   extrair base HTTP compartilhada só quando houver o 3º client (GPM).

**Verificação:** **suíte completa `2 failed, 433 passed, 3 skipped`** (os 2 são os
pré-existentes do sinan; +29 testes FIRMS). Bugs `quote` ausente e colisão `source`
foram pegos por teste e corrigidos antes do commit.

**Bloqueio/limitação:** **não validado ao vivo** (sem MAP_KEY no ambiente). Testado só
com mocks. Os caminhos de endpoint e o parsing de CSV seguem a API documentada do FIRMS,
mas a primeira execução real com chave deve ser conferida. Para validar localmente:
defina `GUARACI_FIRMS_MAP_KEY` (chave grátis em
`https://firms.modaps.eosdis.nasa.gov/api/map_key/`) e rode um job pequeno
(ex.: `country=BRA`, janela de 1–2 dias).
